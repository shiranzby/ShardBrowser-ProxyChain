# pc7 配置文件夹层级

## 行为

- 个人空间的文件夹菜单可新建子文件夹；编辑文件夹可选择父文件夹或顶层。文件夹名仍全局唯一。
- 侧栏按树显示、可折叠；父文件夹的配置列表、总数、视图计数和问题提示包含子孙文件夹。父级列表保留文件夹列，便于辨认具体归属。
- 同级文件夹可拖动排序，也可通过菜单上移/下移。顺序和折叠偏好按空间保存在本机；快捷键使用同一树顺序。
- 移动文件夹只改变父级引用，整棵子树随行。不能选择自己或自己的子孙为父级；后端同样拒绝循环或不存在的父级。
- 重命名同步修正子级父引用，保留配置原始归属、外观及排序位置。删除仅删除当前容器；其直属配置按原来的保留/回收站选择处理，子文件夹和其配置保留并提升一级。确认框明确说明此规则。

## 数据兼容与权限

`folders.json` 升级为 version 2，新增可选 `parents` 映射。原文件夹名称和 Profile 的 folder 字段不改为路径；原来含 `/` 的名称仍是字面名称。version 1 读取时父引用为空。新建/移动的父引用与外观同一次原子替换写盘；保存失败不会先提示成功。旧版 Launcher 遇到 version 2 会拒绝读取，避免无意写回时丢失层级。

层级索引不可读时，重命名和删除现在明确拒绝，在改变任何配置之前保留索引和配置原字节。包含“将配置移到回收站”的 UI 流程也在逐个移动前验证。原来的“外观文件损坏仍继续操作”契约不适用于保存关系数据的 v2；损坏 JSON、未知未来版本和非法父关系类型均有负例。正常 v1/v2 文件仍可重命名和删除。跨多个配置文件的后续磁盘 I/O 故障沿用原有处理，此门槛不宣称跨文件事务原子性。

团队服务器当前 Folder schema/API 只有 name、color 和 profiles，没有 hierarchy metadata。客户端不会把本机父子关系解释为团队权限继承；团队空间隐藏层级入口，`folder_set_parent` 从后端拒绝。个人配置继续按已有设置同步，层级目前仅此电脑保留。跨机层级需要同时升级服务端 schema、API、客户端冲突 hash 与迁移，不可仅追加一个会被旧服务端忽略的字段。

## 定向验证

- Rust：旧版读取/新版本落盘、循环与缺失父级拒绝且文件字节不改、重命名父边、删除提升子级、profile-only 父目录保留、导入循环收敛；团队空间写入口负例。
- TypeScript：树顺序、子孙筛选、字面斜杠名、异常环/孤儿/对象属性名、重命名与删除不可变规则；旧前端存储迁移和写入 epoch 契约。
- Headless UI：新建两层并刷新、父级聚合、折叠/展开、重命名/删除保留子配置、移动子树、防循环、保存失败重试、同级排序及重启、团队隔离。

测试使用合成 mock 和临时目录；不涉及用户实际资料、运行中的前台窗口或桌面 EXE 验收。完整回归及候选构建由主任务统一执行。
