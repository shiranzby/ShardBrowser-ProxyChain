# TNB 提取失败诊断（2026-11-16）

## 结论

当前 TNB 提取失败的主要原因是供应商来源 IP 白名单，不是代理节点账号密码格式，也不是 ShardBrowser 没有发出请求。

对 `usdata.adv.tnbproxy.com:9090/gen` 的脱敏请求观察到：

- TCP/HTTP 请求可到达服务器；
- HTTP 状态为 200；
- 响应体是 JSON 业务错误，`code=403`；
- 业务含义为请求出口 IP 不在白名单。

因此，HTTP 200 不能当作提取成功；必须继续解析业务响应。

## 凭据边界

TNB 在产品中分为两类凭据：

1. API 提取凭据：只用于调用 `/gen` 的 HTTP Basic Auth；
2. 代理出口凭据：只在 TNB 返回代理行没有用户名/密码时补到生成的代理实例。

代理出口账号密码不能替代 TNB 的来源 IP 白名单。即使 API 凭据正确，白名单不满足时仍会返回业务拒绝。

## 不同路由下的白名单出口

TNB 检查的是它实际收到请求时看到的公网来源：

| ShardBrowser 路由 | TNB 看到的来源 |
|---|---|
| 直连 | 本机公网出口 |
| 系统代理 | 系统代理的公网出口 |
| 第一层代理 | 第一层代理出口 |
| 代理链 | 实际到达 TNB 的上游出口 |

使用代理链测试 TNB 时，白名单必须包含该请求路径的真实出口，而不是本地局域网地址。

## 产品处理

后端现在识别 HTTP 200 + `code=401/403`，映射为 `tnb_whitelist_required`；前端显示明确的白名单提示，不再笼统显示“提取失败”。

该修复不会绕过供应商白名单，也不会将失败结果降级为直连或伪造代理实例。
